协同优化

两个模型优化目标不同，但 rollout 数据来自对方，用对方采样轨迹校准自身目标，形成互相供数、互相约束的协同优化。

优势函数融合

优势不是简单相加：关注 A = Σ w_i A_i 的融分公式，也可用几何平均等非线性融合，惩罚“偏科”的奖励项。

优化方向约束

用惩罚函数限制更新方向，防止模型为了单一奖励过度偏离；约束项可以和 KL、margin 或安全奖励共同工作。

归一化顺序

先对各目标分别计算相对优势，再加权求和，与先融合奖励再归一化会得到不同训练信号；相关方向可参考 NVIDIA GDPO。

Projection Optimization

把优化目标限制在凸包内，将当前奖励向量投影到凸包得到投影点 d，再由 d 推出对应权重。

Prompt 条件偏好

不同问题有不同价值偏好，奖励权重应随 Prompt 调整；例如 ArmoRM 用路由/混合方式表达样本级奖励偏好。

02 · POLICY OPTIMIZATION

Constrained Reward GRPO

同一 Prompt 采样 \(G\) 条回答，HCRS 先构造奖励 \(R_i\)，再用组内相对奖励形成优势

GRPO Objective + Group Advantage
\[ \mathcal L=-\frac1{\sum_iT_i}\sum_{i,t}\Big[\min\big(\rho_{i,t}\hat A_i,\operatorname{clip}(\rho_{i,t},1-\epsilon,1+\epsilon)\hat A_i\big)-\beta D_{\mathrm{KL}}\big(\pi_\theta\parallel\pi_{\mathrm{ref}}\big)\Big] \]
\[ \hat A_i=\frac{R_i-\bar R}{\sqrt{\frac1G\sum_k(R_k-\bar R)^2+10^{-8}}} \]
Reward Function
\[ R = r_1 \cdot \left(w_2 \operatorname{Norm}(r_2) + w_3 \operatorname{Norm}(r_3)\right) \]

\(r_1\)规则约束：格式、错误字符、重复与长度

\(r_2\)相关性：LLM-as-Judge 判断兴趣是否贴合输入

\(r_3\)个性化：主动创作精排模型分数

工业实践 · Creation Memory Training & Impact

第六页的起点是数据：训练集不是直接使用模型生成结果，而是先做拒绝采样第一维是相关性，由 LLM-as-Judge 判断兴趣总结与原始输入是否相关、是否有代表性；第二维是个性化，把改写后的兴趣点接入主动创作精排，用精排分过滤低价值样本这些可信样本会被组织为 In-Context Distillation 所需的 few-shot 示例

蒸馏采用两阶段路径：先让中等规模模型吸收闭源 Teacher 的推理能力，再蒸馏到服务侧小模型，以兼顾效果与线上成本随后用 GRPO 做业务对齐：同一 Prompt 采样多条回答，HCRS 为每条回答计算奖励，奖励再被转换为组内相对优势并进入 GRPO 目标

HCRS 中，规则奖励守住格式、长度和去重等质量底线；相关性奖励衡量内容贴合；个性化奖励直接使用主动创作精排信号业务侧，短期 Creation Memory 经豆包社区 MLLM-Emb 转为 Embedding 序列并输入精排模型，最终带来三项线上指标提升

工业实践 · Generative Suggestion Recommendation · 返回第 2 页

第七页介绍 Generative Suggestion Recommendation它和前面的 Creation Memory 是连续的：Memory 负责把用户创作兴趣沉淀出来，这一页则负责把这些兴趣变成能被推荐系统分发的主动创作建议

项目动机主要有三点第一，固定 PGC 候选数量有限，难以覆盖几百万日创作用户的个性化兴趣第二，分发存在明显热度偏差，头部 gid 占据大部分流量第三，Suggestion 推荐不只是语义相关，还要能基于基础兴趣做延申和发散，所以需要生成式候选

方法上先做 Interest Selection：新用户用 UCB Boost 平衡探索和利用；兴趣很多时，用回访兴趣和未反应兴趣构造正负样本，和用户画像做对比学习，得到共鸣打分器随后进入 Suggestion Generation：围绕采样兴趣生成 Prompt 和展示文案，用拒绝采样、两阶段 In-Context Distillation 训练，再通过多目标帕累托偏好对做 DPO 对齐最后，生成候选写入 Abase，推荐服务侧独立召回、安审过滤、精排打分和打散透出，形成端到端闭环

① 上下文管理

长任务不爆窗口

要解决什么

对话越长、工具输出越大，上下文就越容易被撑爆R-Agent 用两条线治理它

请求前压缩

  • 估算 messages + tools 的 token（对中文/JSON 适度高估更安全）
  • 占用达到 0.8 就压缩：把较早历史合并成一条 system 摘要（用户重点 / 助手决策 / 工具结果 / 系统信息），压到 0.55
  • 只压旧的：保留最近 16 条完整消息，且保证一次工具调用和它的结果作为整体，不切成“孤儿”

工具输出后外置

  • 单条输出 > 80k 字符就落盘，上下文只留摘要和路径；本轮聚合 > 160k 时从最大项开始外置
  • 之后用 artifact_inspect / search / slice 有界读回，绝不整块塞回上下文

  • 按文件的修改时间和大小检测 tools/*.py 变化，改完工具不用重启，也能手动 sys_reload 刷新

隔离执行（核心亮点）

  • 普通工具在独立子进程里跑，带超时：到点先 terminate 再 kill，返回结构化超时错误
  • 支持取消：Esc 中断能及时终止子进程工具崩溃、卡死、超时都被隔离，不会拖垮主循环

上下文过滤

  • 主循环支持白名单 / 黑名单，Cockpit 的“Tools 开关”就是靠它控制某次请求是否带上某个工具
tools/registry.py · tools/sys_tools.py
③ Safety 边界

危险操作先审批，再执行

命令风险分级

  • 灾难级直接拒绝：rm -rf /、mkfs、写裸盘、fork bomb 等根本不执行
  • 高危需审批：提权、删除、磁盘挂载、包安装、git reset --hard、越出工作区、curl 管道到解释器等
  • 先剥离 heredoc 和引号字面量再扫描，避免把示例字符串里的危险词误判

人类审批 token

  • 高危命令首次调用不执行，返回随机 token（TTL 10 分钟，一次性）；Agent 必须先说明命令、风险、影响
  • 用户同意后带 token 再调用才执行；审批状态跨隔离子进程共享

沙箱 + 子 Agent 收权

  • 越出工作区的读写删走审批；子 Agent 禁用递归委派、长期记忆、语音等副作用工具
tools/sys_tools.py · tools/file_tools.py · core/prompt_builder.py
④ Todo / Delegate

复杂任务拆成父子 Agent 协作

两层分工

  • Todo 看板：共享的状态 / 规划板——树状任务、拓扑依赖、claim 租约只有 pending 且依赖都完成的叶子任务能被执行
  • Delegate 引擎：真正干活的地方，每个子任务启动一个全新 Agent，线程池并行（默认 3，上限 10）

为什么不会“上下文互相污染”

  • 子 Agent 只拿到自包含的目标，明确“你不是全局调度者”
  • 无论成功 / 超时 / 截断，子上下文都落盘归档，只把路径写回看板；父进程默认只读 digest，不回灌子进程的完整对话
  • 超时不算失败，而是标记 blocked、交还父进程重新规划；整棵树完成后再统一清理
